## Seed

- Current model: a Case is an optional grouping of Threads with no Status of its own; a Thread is in at most one Case (FR-12, I-3, decisions in `docs/prd.md` around #529/#539). Cases have a list page and a Linear-style page with one card per Thread (`docs/design/console.md` #91, #98).

## Decisions so far (Jeremy, 2026-10-13 grilling)

| Topic | Decision |
|---|---|
| What a Case is | One goal with an end: a support issue, a deal or onboarding, or a bowtie-funnel goal such as "get this person to respond". When a goal is met, the next goal is a new Case. |
| CRM | A Case may match one Attio record (for example a deal). No Attio field on the Case: a link, if wanted, goes in the description. No data copied, no integration. Funnel stage stays in Attio. |
| Case Status | Pure roll-up: the earliest stage among its Threads, in the order Todo, Snoozed, Done, Ignored (any Todo makes it Todo; else any Snoozed; else any Done; all Ignored makes it Ignored). Jeremy never sets it. Accepted trade-off: a Case whose Threads are all Done shows Done even if its goal (for example the Attio deal) is still open. Supersedes a brief earlier choice of a manual, gated "Resolved". |
| Outcome | No outcome recorded (no Met/Dropped). |
| Work surface | Cases become a rail section with four views, Todo, Snoozed, Done, Ignored (no All), replacing the browse "Cases" entry; key 8 opens Cases › Todo. Thread views group Threads under Case header rows; the "No case" group comes first. |
| Membership | Keep one Case per Thread (I-3). |
| Empty Case | A Case can be created from the Cases view before any Thread joins it; with no Threads it is Todo. |
| Grouped Thread views | Each Case header row shows the title and counts of its Threads in every Status (for example 2 todo · 1 snoozed · 4 done). After "No case", groups sort by their oldest Thread in the view. |
| Out of scope | Starting a new Thread from inside a Case. |

## Research: how other tools complete a parent of several conversations

From official docs, gathered 2026-10-13. Salesforce is only partly verified because its help pages blocked fetches.

1. **Manual close on the parent.** Used by the Salesforce Case, the HubSpot ticket, and the Zendesk ticket.
   - Each pairs it with reopen-on-inbound: Zendesk reopens Solved tickets on reply; HubSpot's reopen is configurable.
   - Sources: [Zendesk lifecycle](https://support.zendesk.com/hc/en-us/articles/8263915942938), [HubSpot reopening](https://knowledge.hubspot.com/help-desk/manage-reopened-tickets-in-help-desk), [Salesforce milestones](https://trailhead.salesforce.com/content/learn/modules/entitlement-management-for-lightning-experience/set-up-milestones).
2. **Parent completion pushes to the children.** Zendesk Problem→Incident, Intercom tracker tickets, and closing a HubSpot ticket.
   - Sources: [Zendesk problem/incident](https://support.zendesk.com/hc/en-us/articles/4408835103898), [Intercom tracker](https://intercom.com/help/en/articles/8300306-how-to-manage-tracker-tickets).
3. **Children gate the parent.** A Freshdesk parent can close only when every child is resolved.
   - Source: [Freshdesk](https://support.freshdesk.com/support/solutions/articles/226196-when-can-we-close-the-parent-ticket-).
4. **Parent completion creates "close the loop" work on the children.** Plain and Front do this with linked Linear/Jira issues.
   - Sources: [Plain Linear](https://www.plain.com/docs/product/integrations/linear.md), [Front Linear](https://help.front.com/en/articles/2343).

The chosen pure roll-up derives the parent from its children. None of the surveyed tools uses that alone; Jeremy accepted the all-Done-but-goal-unmet trade-off.
